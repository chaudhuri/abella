# Plan: Abella Web

**Version:** v11 (2026-10-23)

**Status:** working plan. v11 records the GitHub OAuth sidequest and its
production deployment on 2026-10-23.

**Naming:** the product and page are **Abella Web**; the deployment path
is `/web/`. All new directories, files, npm scripts, CSS classes, and
localStorage keys use `web`, not the legacy label. The historical branch
is referred to as the legacy browser branch.

**Confirmed decisions:** static client-side prover; prover runs in a
Web Worker; editable multi-file projects. The OCaml-to-browser backend is
**wasm_of_ocaml**, selected by the Phase 0 bake-off run on 2026-10-22
(§5.8); the same adapter and worker API also build with js_of_ocaml, which
remains a buildable diagnostic/fallback target. Imports are compiled from
source in the browser on first use, and the generated `.thc` is kept in
the virtual project file system for the rest of the session. Native `.thc`
files are not bundled (they are tied to the native binary hash). Native
compilation of the full CCS example took ~30s here, so the session cache
matters; cross-session persistence is a possible later addition.

## Revision note: GitHub OAuth

v11 changes only how a GitHub token is obtained. Public reads remain
token-free; fine-grained PATs remain for least-privilege users and as a
fallback. `Sign in with GitHub` uses a popup, PKCE S256, a static
callback page, and a small Cloudflare Worker at
`oauth.abella-prover.org` that holds the OAuth client secret. The
production OAuth App is owned by the `abella-prover` GitHub
organization. Tokens stay in `sessionStorage`. The static site and
Worker are deployed, Cloudflare proxies the web origins, and the
public-scope production connect and commit round trip succeeded. The
private-repository opt-in still needs a real private test repository.
The detailed design, phase record, and deployment notes are in
`plans/abella-web-github-oauth.md`; `README_Web.md` and
`support/oauth-worker/README.md` cover operation.

## Plan versioning

This plan is a versioned document, stored in `plans/abella-web/`:

- each substantive revision is published as a new file `vN.md`; a
  published version is immutable for substantive content (typo and
  formatting fixes are the only exception, and are logged);
- `plans/abella-web/README.md` is the index and points to the latest
  version;
- the latest version is the source of truth; older versions are kept for
  history;
- scope changes, design changes, and new decisions require a new version
  and a one-line entry in the README version log;
- typo-only or formatting corrections may be folded into the current
  version, but must still be recorded in the README version log/commit
  history;
- commits that change the plan should name the plan version they
  produce.

The current version is **v11**, created 2026-10-23. It records the
completed Phase 0 backend bake-off (wasm_of_ocaml), the completed Phase 1
core, the Phase 2 frontend MVP, the checking/feedback sidequest, the
Phase 3 UX work, the timeboxed Phase 3b local-directory backend, the
Phase 4 repository hardening, the Phase 5 workspace abstraction, the
Phase 6a GitHub read/commit implementation, and the GitHub OAuth
sidequest with its production deployment.

## 1. Objective

Rebuild the defunct legacy browser branch's interface on top of current
Abella (`master`), using:

- modern TypeScript,
- CodeMirror 6 for every file editor,
- no application framework (no Angular, jQuery, Bootstrap JS),
- the existing structured JSON trace output (`abella -a`) rather than
  scraping the terminal transcript.

The result should feel like the old "Abella in your browser" page, with
current Abella's multi-file developments:

- edit `.sig`, `.mod`, and root `.thm` files in the browser;
- load a curated multi-file example (including `Import`s) or start a
  scratch project;
- see the project's files in a sidebar and edit imported modules;
- press `Ctrl/Cmd-Enter` to process the root reasoning file up to the
  cursor;
- see the current goal and Abella's messages in a side pane;
- edit an already-processed region and have the prover state rewind
  automatically;
- process the whole file or reset the session;
- keep the project contents in `localStorage`.

The page should be deployable as static files under `https://abella-prover.org/web/`.

Feature parity with the old interface:

| Legacy browser UI | Abella Web |
| --- | --- |
| `.sig`/`.mod` editors | project file sidebar + CodeMirror |
| `.thm` editor | project file sidebar + CodeMirror |
| load example / start from scratch | same, plus multi-file projects |
| `Ctrl-Return` process to cursor | same |
| `Ctrl-Shift-Return` blocking | not provided (removed) |
| process full / reset | same |
| status colours | status badge |
| processed-region marker | CodeMirror decoration |
| rewind on edit | same |
| localStorage | project JSON |
| Ace | CodeMirror 6 |
| Angular/jQuery/Bootstrap | none |

## 2. What exists today

### Legacy browser branch (`origin/try`, `myfork/try`)

- A single HTML page built with Angular 1, Bootstrap, and jQuery.
- An Angular controller using Ace editors; incremental processing, undo
  history, localStorage, and a processed-region marker.
- Ace syntax modes for Abella and λProlog.
- `src/js/abella_js.ml`: a js_of_ocaml adapter exposing
  `abella.batch`, `abella.reset`, `abella.process1`.
- `src/abella_driver.ml`: extracted driver logic from `abella.ml`.
- `src/file_cache.ml`: an in-memory file cache for the `.sig`/`.mod` pair.
- A self-contained examples directory with no `Import` and no
  `accum_sig`.

The legacy branch is based on an old Abella and an old build system
(ocamlbuild/omake). Its JS API is text-oriented: each call returns
`{status, output}` where `output` is HTML-flavoured terminal text.

### Current `master`

- `src/abella.ml` contains both the driver and the Cmdliner CLI.
- `src/output.ml` already supports an annotation mode:
  `abella -a -o file.json` emits a JSON array of messages:
  - `top_command` (`range`, `command`)
  - `proof_command` (`thm_id`, `theorem`, `command`, `range`,
    `start_state`, `end_state`)
  - `system_message` (`severity`, `message`)
  - `link` (`source`, `url`)
- `Prover.state_json ()` renders a sequent as
  `{name, vars, hyps, goal, more}`.
- `State.Undo` supports snapshots, `push`, `undo`, `back n`, `reset`.
- `src/source.ml` abstracts file opening behind an `openers` list.
- `support/` contains a modern TS build (esbuild, Tailwind v4,
  TypeScript, `tsc --noEmit`) used by `abella_doc`.
- `support/ts/abella_doc.ts` already renders JSON traces and sequents
  for the static documentation pages. Its sequent renderer and syntax
  highlighting regexes are directly reusable.

This means the hard parts of the old branch (incremental processing,
undo, JSON trace) still exist or are better in `master`. What is missing
is a JS build of the prover and a new frontend.

## 3. Recommended architecture

### 3.1 Static client-side prover (confirmed)

Compile Abella to a browser target and run it entirely in the browser.
No server, no session state, no database. Deploying is a static file
copy.

The compiler backend was selected in Phase 0 from a real bake-off:

- **wasm_of_ocaml (selected)** — part of the js_of_ocaml project and
  actively developed; WasmGC + tail calls. It was consistently about
  **2.3× faster** than js_of_ocaml on the import-heavy CCS benchmark and
  about **2× faster** on individual proof commands, with comparable
  artifact size (§5.8). Costs: a higher browser floor
  (Chrome/Edge 119+, Firefox 122+, Safari 18.2+), Binaryen at build time,
  a JS launcher plus `.wasm` assets, and `'wasm-unsafe-eval'` in the CSP.
- **js_of_ocaml (fallback/diagnostic)** — proven by the old branch;
  broader support; single JS artifact; simplest deployment. It passed
  every Phase 0 gate and remains a buildable target, but is not the
  deployed engine.

Phase 0 built both from the same `abella_js.ml` and selected wasm on
correctness, performance, and deployment results (§5.8).

```
┌──────────────────────────── browser ────────────────────────────┐
│                                                                 │
│  CodeMirror 6 editors (TypeScript)                              │
│      │                                                          │
│      ├── command scanner ──> session controller                 │
│      │                            │  postMessage                │
│      │                            ▼                             │
│      │                     Web Worker (required)                │
│      │                            │                             │
│      │              abella_js.js / .bc.wasm.js + assets         │
│      │                            │                             │
│      │                     Abella_driver ──> abella_lib         │
│      │                            │                             │
│      │                     Output collect ──> JSON messages     │
│      │                            │                             │
│      └── trace/goal renderer <────┘                             │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

Why this is the right default:

- It matches the legacy browser experience and deployment model.
- The prover is already pure OCaml apart from a handful of file-system
  calls; those can be abstracted behind `Source`.
- A server would need process isolation, timeouts, resource limits,
  session cleanup, and ongoing operations for a public demo page.
- A static page can live on the existing `abella-prover.org` rsync
  workflow.

The alternative (server-backed interactive Abella) is described in
§11. It is not recommended for v1.

### 3.2 Run the driver in a Web Worker (confirmed)

Abella commands such as `search`, `induction`, or large `case` analyses
can take seconds. Running the compiled prover on the main thread would
freeze both CodeMirror and the page. Put the compiled prover in a Web
Worker and speak a small request/response protocol. Both backends load
as a classic worker: js_of_ocaml via
`importScripts("abella_js.js")`; wasm_of_ocaml via
`importScripts("abella_js/abella_js.bc.wasm.js")`, whose generated
launcher fetches the `abella_js/abella_js.bc.wasm.assets/*.wasm` files.
The Phase 0 check confirmed that the launcher locates its assets relative
to the **worker script URL**, so the wasm worker must live inside
`web/abella_js/` (see §9.2).

```ts
// main -> worker
{ id, type: "init",    files: ProjectFile[], root: string }
{ id, type: "process", command: string, start: SourcePos }
{ id, type: "back",    count: number }
{ id, type: "reset",   files: ProjectFile[], root: string }

// worker -> main
{ type: "result", id, ok: true,
  result: { status: "ok" | "error", messages: Message[] } }
{ type: "result", id, ok: false, error: string }
{ type: "progress", id, stage: "compiling", module: string }
```

Benefits:

- the UI stays responsive;
- "Reset" can terminate the worker, guaranteeing clean state;
- "Stop" can terminate a runaway command (state is lost, which is
  acceptable for a demo);
- the same driver API can be used on the main thread as a fallback.

The frontend controller treats the driver as async, so the worker can be
replaced by a main-thread implementation during debugging without
changing the UI. The production path is always the worker.

## 5. OCaml changes

### 5.1 Extract the driver from `abella.ml`

Move everything in `src/abella.ml` before the "Command line and startup"
section into a new `src/abella_driver.ml`:

- `Setup`
- `process1`, `process_proof1`, `process_top1`
- `set`, `import`, `read_specification`, `compile`, etc.
- `welcome_msg`
- `position`, `type_inference_error`, `query`, etc.

`src/abella.ml` then becomes only:

- Cmdliner argument parsing,
- signal setup,
- `Output`/`Setup` configuration,
- `while true do Abella_driver.process1 () done`.

Because `abella_lib` is a wrapped library and its dune stanza excludes
only the known executables, `abella_driver.ml` becomes
`Abella_lib.Abella_driver` automatically.

Expose (no `.mli` currently, but document) at least:

```ocaml
val process1 : unit -> status
val back : int -> unit
val welcome_msg : string
val initial_snapshot : State.snap
val on_import : (string -> unit) option ref
module Setup : sig
  val mode : [`batch | `interactive | `switch] ref
  val annotate : bool ref
  val recurse : bool ref
  val input : string ref
  val lexbuf : Lexing.lexbuf ref
  val compiled : (module Source.THM) option ref
  val unfinished : string list ref
  val import_mode : [`thc | `source | `auto] ref
  val trust_compiled : bool ref
end
```

`process1` currently returns `unit` and swallows errors into
`system_message` output. Change it to return `` `ok`` / `` `error``:

- normal return -> `` `ok``
- each exception handler that prints an error -> `` `error``

The CLI ignores the return value, so behavior is unchanged.

#### CLI compatibility guarantee

The standard CLI and interactive workflow is a hard compatibility
requirement, not an afterthought:

- `src/abella.ml` keeps the same Cmdliner surface:
  `-f/--flags`, `-i`, `-o`, `-c`, `-a`, `-N`, `-M`, `--verbosity`, and
  the positional `.thm` file.
- Batch mode, interactive mode, and `-i` switch mode keep their
  behavior and prompt text.
- The `-a` JSON annotation format (message types, field names, message
  order) is unchanged.
- The `.thc` format is unchanged: `write_compilation` still marshals the
  same values, including `Lazy.force Version.self_digest`; the reader
  changes from channels to `Marshal.from_string`, which reads the same
  bytes.
- `import_mode` defaults to `` `thc ``; `import_load`'s native path is
  the existing one.
- `Output.Collect` is additive; `Channel`, `Buffer`, and `Json` keep
  their behavior.
- `Version`/`Xdg` laziness changes only *when* the executable digest and
  XDG directories are computed, not their values.
- No new mandatory runtime dependency: the browser backend
  (`js_of_ocaml` or `wasm_of_ocaml`) is build-time optional for the web
  target.

Regression coverage:

- `make all-release`, `dune runtest`, and the existing
  `test/test.mk` example run must pass unchanged;
- a golden test runs `abella -a` on a few representative examples and
  compares the JSON to pre-change output;
- an interactive smoke test pipes a short theorem script through
  `abella` and compares the transcript;
- `abella -i file.thm` is exercised (batch then switch to interactive).

### 5.2 Verify `back`

With `State.Undo` as it stands, `process1` pushes one snapshot before
each command. After `k` successful commands, `State.Undo.back k` restores
the state from before the first of those commands. Add a small native
regression test or a toplevel check during implementation to confirm:

- process `A`, `B`, `C`;
- from the resulting state, `back 1` leaves the state after `B`;
- from the resulting state, `back 2` leaves the state after `A`;
- from the resulting state, `back 3` returns to the initial state.

Do not route `back` through `process1` in the JS adapter (unlike the old
`#back.` command, which needed `back 2` because the `#back.` command
itself pushed a snapshot).

### 5.3 Virtual project file system in `src/source.ml`

Add an explicit in-memory project map for text files and generated `.thc`
bytes:

```ocaml
let virtual_files : (string, string) Hashtbl.t = Hashtbl.create 19

let canon path =
  (* strip leading "./", collapse "." and ".." segments, normalize
     separators *) path

let add_virtual path contents = Hashtbl.replace virtual_files (canon path) contents
let virtual_exists path = Hashtbl.mem virtual_files (canon path)
let virtual_contents path = Hashtbl.find virtual_files (canon path)
let clear_virtual () = Hashtbl.clear virtual_files

(* set when a browser-generated .thc is ready *)
let thc_trusted : (string, bool) Hashtbl.t = Hashtbl.create 19
let set_thc_trusted path trusted =
  Hashtbl.replace thc_trusted (canon path) trusted
let is_thc_trusted path =
  Hashtbl.find_opt thc_trusted (canon path) |> Option.value ~default:false
let clear_thc_trust () = Hashtbl.clear thc_trusted
```

`canon` strips a leading `"./"` and normalizes separators so that
`Filepath.normalize` results (`"./name"`) and bundle keys (`"name"`)
agree.

`open_virtual_file` returns a `SOURCE` with:

- `mtime = 0.`,
- `dir = Some (Filename.dirname path)`,
- `lex` via `Lexing.from_string` plus `Lexing.set_filename`.

Put it at the front of `openers`. `Accumulate.read_lp`, the
`Specification` top command, `accum_sig`/`accumulate`, and `Import`
path resolution then work without any change.

Do **not** use `Sys_js.create_file`; an explicit virtual layer is
testable on native OCaml and avoids pretending the browser has a real
file system.

#### In-browser `.thc` cache (required)

Native source compilation is expensive (the full CCS development takes
~30s natively, likely longer in JS). The browser therefore generates
`.thc` files itself and keeps them in the virtual project FS:

- on first import of a module, source-compile it (§5.7);
- serialize the four compiled values into the same `.thc` layout that
  native Abella uses, with `Marshal.to_string`, before restoring the
  parent state;
- add the bytes to the virtual FS as `module.thc` and mark the entry
  trusted;
- on later imports in the same session, use the `.thc` fast path;
- a project edit or `init`/worker reset clears the cache.

Because the `.thc` is generated by the same JS runtime that reads it,
there is no native/JavaScript Marshal compatibility risk and no bundled
`.thc` to refresh when the Abella binary changes.

Required support:

- extend `Source.THM` with `val thc_contents : unit -> string`;
- native implementation reads the file; virtual implementation returns
  the in-memory bytes;
- `read_thm` for a virtual `.thm` returns `is_stale` from a trust flag
  and a no-op `marshal`/`close`;
- change the `.thc` reader to use `Marshal.from_string` with a cursor
  helper:

```ocaml
let marshal_reader (s : string) : unit -> 'a =
  let buf = Bytes.unsafe_of_string s in
  let pos = ref 0 in
  fun () ->
    let v = Marshal.from_string s !pos in
    pos := !pos + Marshal.total_size buf !pos ;
    v
```

(`Marshal.total_size` takes `bytes`; `Marshal.from_string` takes
`string`. The string is not mutated.)

This avoids in_channels and works identically in native OCaml and
js_of_ocaml. It also simplifies the native import path (no
`open_in_bin`).

Trust model:

- virtual `.thc` files generated by the browser are trusted
  (`Source.set_thc_trusted path true`);
- the `Version.self_digest` check is skipped for them
  (`Setup.trust_compiled := true`);
- there is no upload path for untrusted `.thc` data in v1.

#### JS startup hazards (required)

Two module-initialization side effects must be removed before the
library can start in a browser:

1. `Version.self_digest` currently calls `Digest.file
   Sys.executable_name` at module load. Make it lazy:

   ```ocaml
   let self_digest = lazy (Digest.file Sys.executable_name)
   ```

   Native code uses `Lazy.force` where needed. Crucially, guard
   `write_compilation` so it does not force the digest when
   `Setup.compiled = None`:

   ```ocaml
   let write_compilation () =
     match !Setup.compiled with
     | None -> ()
     | Some _ ->
         marshal (Lazy.force Version.self_digest) ;
         ...
   ```

   Otherwise the source-import sandbox (which sets `compiled := None`)
   would still force `Digest.file` in JS. Add
   `Setup.trust_compiled : bool ref` (default `false`, set to `true` by
   the web adapter) and skip the digest comparison for browser-generated
   `.thc` files.

2. `Extensions.Xdg` computes `cache_dir`/`config_dir`/`state_dir` at
   module load, and its `/` operator calls `Sys.file_exists` and
   `Sys.mkdir`. That is not safe in a browser (and `HOME` may be empty).
   Make the XDG paths lazy:

   ```ocaml
   let xdg_cache_dir = lazy (
     Sys.getenv_opt "XDG_CACHE_HOME" |>
     Option.value ~default:(home / ".cache"))
   let cache_dir = lazy (Lazy.force xdg_cache_dir / abella / "run")
   (* likewise for config_dir and state_dir *)
   ```

   Note that `xdg_cache_dir` must be lazy too: its eager default calls
   the `/` operator, which creates directories. The only current user is
   `Source.read_thm` for non-`.thm` paths, which the web source-import
   path never reaches. Update it to `Lazy.force Xdg.cache_dir`.

The rest of the library was audited: the only module-initialization
file-system work was `Version.self_digest` and `Xdg`; both are lazy now.
`abella_doc` and `abella_dep` still do file-system work, but they are
separate executables excluded from `abella_lib` and never linked into the
browser adapter.

#### Project paths

The project map uses project-relative source paths, e.g.
`examples/process-calculi/ccs/ccs_core.thm`. The root reasoning file's
path is passed as `Setup.input`, so `Specification "ccs"` and
`Import "ccs_core"` resolve to the same keys that the bundle registered.
For a scratch project, paths are `empty.sig`, `empty.mod`, and
`main.thm`.

`Setup.input` and the other `Setup` fields are currently plain refs;
the adapter sets them after `State.reload` and restores them around any
sandbox compile (see §5.7).

The frontend does not derive the spec name from the file contents. It
sends the complete file map plus the root path, which is simpler and
supports arbitrary directory layouts.

### 5.4 Drainable JSON output in `src/output.ml`

Current annotation mode accumulates messages into a `Json` destination
but only writes them at `flush` time to a channel. Add an in-memory
collection mode:

```ocaml
type t =
  | Channel of out_channel
  | Buffer of { out : Buffer.t ; err : Buffer.t ; base : out_channel }
  | Json of { mutable out : Json.t list ; base : out_channel option }
  | Collect of { mutable out : Json.t list }
  | Null

val collect_mode : unit -> unit
val drain : unit -> Json.t list
```

`drain` returns messages in chronological order (reverse the internal
cons-list) and clears the accumulator. `flush` is a no-op for
`Collect`.

This is a small, low-risk change. `abella -a` keeps its existing
behavior.

### 5.5 JS adapter: `src/js/abella_js.ml`

The adapter is a small module that owns the JS-facing surface shared by
both browser backends. The initial snapshot lives in `Abella_driver` so
native tests can reuse it:

```ocaml
(* in abella_driver.ml, after all State refs are defined *)
let initial_snapshot = State.snapshot ()

(* in src/js/abella_js.ml *)
let re_init (files : (string * string * bool) list) (root : string) =
  State.reload Abella_driver.initial_snapshot ;
  State.Undo.set_enabled true ;
  State.Undo.reset () ;
  Source.clear_virtual () ;
  Source.clear_thc_trust () ;
  List.iter (fun (path, contents, is_binary) ->
      Source.add_virtual path contents) files ;
  (* generated .thc files are registered and trusted during import *)
  Setup.mode := `interactive ;
  Setup.annotate := true ;
  Setup.recurse := false ;
  Setup.import_mode := `auto ;
  Setup.trust_compiled := true ;
  Setup.input := root ;
  Output.collect_mode () ;
  ignore (Output.drain ())
```

The `(path, contents, is_binary)` tuple carries text files as-is. The
binary flag marks generated `.thc` files; base64 decoding uses the
existing `base64` library if the main thread transfers cached bytes.

API exposed as `globalThis.Abellajs`:

```ts
interface Abellajs {
  init(files: ProjectFile[], root: string): Result;
  reset(files: ProjectFile[], root: string): Result;
  process(command: string, start: SourcePos): Result;
  back(count: number): Result;
}

interface ProjectFile {
  path: string;       // project-relative, e.g. "ccs/ccs_core.thm"
  contents: string;   // text, or base64 for a cached .thc
  binary?: boolean;   // reserved for optional persisted .thc caches
}

interface Result {
  status: "ok" | "error";
  messages: RawMessage[];
}

interface SourcePos {
  offset: number;  // UTF-8 byte offset of the command in the document
  line: number;    // 1-based line number
  bol: number;     // UTF-8 byte offset of the beginning of that line
}
```

`process`:

1. `let lb = Lexing.from_string command`
2. set `lb.lex_curr_p` to
   `{ pos_fname = root; pos_lnum = start.line;
      pos_bol = start.bol; pos_cnum = start.offset }`
3. `Setup.lexbuf := lb`
4. `let status = Abella_driver.process1 ()`
5. `let messages = Output.drain ()`
6. return `{status; messages}`

Wrap the call in a `try ... with` that also drains output and returns a
synthetic `system_message` for any uncaught OCaml exception. This is the
last line of defense; normal errors are already turned into messages by
`process1`.

Setting the lexbuf positions to the command's location in the root
document makes Abella's error messages line-aware. **Caveat:** Abella's
`Lexing.position.pos_cnum` counts UTF-8 bytes, while CodeMirror offsets
count UTF-16 code units. The two coincide only for ASCII. Do not use
Abella's `range` fields directly as editor offsets. The command scanner
knows the JS range of every command; use that for diagnostics,
processed-region decoration, and error highlighting. Treat Abella
`range` as advisory. If character-precise mapping is needed later, add a
byte↔UTF-16 offset map for the document.

`init`/`reset` register the complete virtual project (text files; `.thc`
entries are empty at init), clear `Accumulate` caches,
set `Setup.import_mode := `auto` and `Setup.trust_compiled := true`, and
return the welcome message. No `Sys.command` path is ever exercised.
`Import` uses generated `.thc` files when present and otherwise
source-compiles them (§5.7).

### 5.6 Dune / opam / browser backend

`src/js/dune` builds the same `abella_js.ml` for both targets, with
selective enabling via `lib-available`:

```lisp
(executable
 (name abella_js)
 (modes js wasm)
 (modules abella_js)
 (libraries abella_lib js_of_ocaml)
 (preprocess (pps js_of_ocaml-ppx))

  (enabled_if %{lib-available:js_of_ocaml}))

```

Both targets use the same `Js` FFI and the `js_of_ocaml-ppx`
preprocessor. The `enabled_if` clauses require Dune >= 3.17, and the
`wasm` mode requires Dune >= 3.20, so the project is now
`(lang dune 3.20)` (and `abella.opam` requires `dune >= 3.20`).

Build targets:

- js_of_ocaml: `dune build src/js/abella_js.bc.js`
- wasm_of_ocaml: `dune build src/js/abella_js.bc.wasm.js`

**FFI portability (Phase 0 finding).** Property names, numeric keys, and
JSON integers must be converted explicitly when crossing the boundary:
use `Js.string` for property names, `Js.float` for JavaScript numbers /
array indices, and `Js.to_float` when reading numbers back. Passing an
OCaml string or int directly to `Js.Unsafe.get` happens to work under
js_of_ocaml but produces wrong results (or non-cloneable boxed numbers)
under wasm_of_ocaml. The shared adapter follows these rules, so it
behaves identically on both engines.

Build-time requirements:

- js_of_ocaml: `js_of_ocaml`, `js_of_ocaml-ppx` (no system deps).
- wasm_of_ocaml: `wasm_of_ocaml-compiler` (current 6.4.x), plus a
  system **Binaryen 119+** (120 was used in Phase 0). The wasm backend is
  part of the js_of_ocaml release now, but it is a heavier build
  dependency.

Packaging:

- Keep both compilers out of the native runtime package's mandatory
  dependencies; guard the stanzas and have `make web` check for the
  selected backend and print an actionable `opam install ...` message.
- Add the discovered browser floor and CSP/MIME requirements to the
  deployment docs; wasm was selected, so they are mandatory (§9.2).

Both backends passed Phase 0; wasm_of_ocaml was selected (§5.8).
js_of_ocaml remains a buildable fallback if a wasm runtime regression
appears. If both fail, the server architecture in §11 remains the escape
hatch.

### 5.7 Imports and multi-file support (source compile + `.thc` cache)

`Import "name".` normally loads `name.thc`, a `Marshal`ed snapshot of an
already-compiled development. The browser cannot shell out to native
Abella, so the web build compiles imported modules **from source** the
first time and caches the generated `.thc` in the virtual FS.

Add a `Setup.import_mode : [`thc | `source | `auto] ref` setting
(default `` `thc ``). Native `abella` keeps `` `thc ``; the web adapter
sets `` `auto ``. `import_load` behaves as follows:

- `` `thc ``: existing native behavior;
- `` `source ``: always source-compile (tests/debugging);
- `` `auto ``: use `.thc` when
  `Source.is_thc_trusted (modname ^ ".thc")` is true, otherwise
  source-compile and populate the `.thc` cache.

Native users and native `.thc` files are unaffected.

#### Sandbox compile algorithm

On `Import "name"` in source mode:

1. Snapshot the current driver state (`State.snapshot ()`) and save the
   plain refs:
   - `Setup.mode`, `Setup.annotate`, `Setup.recurse`, `Setup.input`,
     `Setup.lexbuf`, `Setup.compiled`, `Setup.unfinished`,
     `Setup.import_mode`, `Setup.trust_compiled`;
   - `Output.dest`;
   - `State.Undo`'s enabled flag (add `State.Undo.is_enabled`);
   - `can_read_specification` (State ref, but save for clarity);
   - the current `current_state` value.
2. Restore the module-initial snapshot
   (`State.reload Abella_driver.initial_snapshot`) to get a pristine
   prover state, then configure the sub-session:
   - `State.Undo.set_enabled false`;
   - `Setup.mode := `batch`;
   - `Setup.annotate := false`;
   - `Setup.recurse := false` (no `Sys.command` in the browser);
   - `Setup.compiled := None`;
   - `Setup.unfinished := []`;
   - `Setup.input := path_of_imported_thm`;
   - `Setup.lexbuf := (Source.read path).lex true`;
   - `Output.collect_mode ()` (so failures can be reported; the messages
     are not merged into the main trace).
3. Loop `process1 ()`. `process1`'s EOF handler raises `AbellaExit 0` in
   batch mode; catch that as success. `AbellaExit 1`, an `` `error``
   return, or any other exception aborts the import with the collected
   error text.
4. While the sub-session state is still live, collect the same four
   values that `write_compilation` marshals:
   `!comp_spec_sign`, `!comp_spec_clauses`, `predicates !sign`, and
   `List.rev !comp_content`, and serialize them **before** restoring the
   parent. The data may share mutable term cells with the global bind
   state, so serializing after `State.reload` could capture the wrong
   values.
5. Serialize into the native `.thc` layout using `Marshal.to_string` for
   each value:
   - a placeholder digest (the browser trusts its own files),
   - `Version.version`,
   - spec sign, spec clauses, predicates, compiled content.
6. Restore the saved snapshot and plain refs and re-enable undo.
7. Add the bytes to the virtual FS as `<modname>.thc`, call
   `Source.set_thc_trusted`, and apply them via the normal
   `import_load_thc` path. Unmarshaling gives the parent fresh values, so
   no sub-session pointers leak into the main state.

The virtual `.thc` is the session cache. A later `Import` in the same
session (including after a rewind) takes the `.thc` fast path. `init`
and worker resets clear the virtual FS, so the cache is per session and
never outlives a project edit.

Nested imports work because the sub-session recursively calls the same
source compiler; the saved parent state protects the outer session. The
`imported` list is a `State.rref`, so each nested session has its own
copy. Add a plain `compiling : string list ref` stack (saved and
restored like the other plain refs) to detect import cycles across
sandboxes; `State.reload` would otherwise hide the parent's `imported`
list from a self-import.

Factor the existing `process_decls` out of `import_load` into a
top-level helper taking `~repl` and `~modname`, so the `.thc` and source
branches share the declaration-application logic. `CImport` declarations
then recurse through the source branch automatically.

Progress reporting: add an optional hook
`Abella_driver.on_import : (string -> unit) option ref`. The source compiler
calls it before compiling each module; the JS adapter forwards a
`{type: "progress", module}` message to the main thread so the status
bar can show "compiling imported module…".

#### Cache lifetime and invalidation

The `.thc` cache lives in the worker's virtual FS:

- it is populated on the first source compile of each module;
- it survives rewind/reprocess within a session, including after
  `State.Undo.back`;
- it is cleared whenever the project text changes (spec, imported
  module, or file set), because the frontend terminates/reset the worker
  before reprocessing;
- it does not survive a page reload; a later enhancement can persist
  `.thc` bytes in IndexedDB, keyed by an app build id and source hashes.

Within a session the project is immutable (any edit resets the worker),
so no per-module hash check is required for the in-memory cache.

#### Risks and mitigations

- **Global state coverage.** `State.snapshot` covers `State.rref`/
  `State.table`/`State.make` values, including term bindings
  (`term.ml` registers a `State.make` for bind state) and prover state.
  A few plain refs need explicit handling:
  - `Typing.clause_map`: restored around a sandbox (native `.thc`
    imports do not carry clause names) and cleared by adapter init;
  - `Unify.local_used`: per-unification scratch, reset at the start of
    each unification call; nothing to restore;
  - `Accumulate.sig_cache`/`mod_cache`: shared across sessions; cleared
    by adapter init and on a specification edit;
  - `Prover.built_ins_done`: set once at startup, never reset.
- **Performance.** Re-running imported proofs in JS can be slow on the
  first use of a module. Mitigate with the generated `.thc` cache (once
  per session), a "compiling imported module…" status, and a curated mix
  of cheap and substantial examples. Add IndexedDB persistence later if
  first-load time is a problem.
- **Correctness.** The sub-session must produce exactly what native
  `write_compilation` produces. The native test `values_match_native`
  compiles a small imported module both ways and compares the four
  values; `ccs_core` was also compared during Phase 0.
- **Reentrancy.** All requests are serialized in the worker, so only one
  sandbox runs at a time.
- **Progress names.** `on_import` receives the canonical module name
  (e.g. `ccs_core`, not `./ccs_core`), so the UI can display it
  directly.

#### Reset contract

A worker reset/`init` (and therefore a project or spec edit) guarantees
a fresh prover state:

- `State.reload Abella_driver.initial_snapshot` restores every
  `State.rref`/`table`/`make`, including the signature, clauses, prover
  state, undo stack, `imported`, and the driver's `current_state`;
- `State.Undo` is reset and re-enabled;
- `Source.clear_virtual` and `Source.clear_thc_trust` drop all project
  files and generated `.thc` bytes;
- `Accumulate.clear_specification_cache` and
  `Typing.clause_map := Term.Itab.empty` drop parse/type caches that are
  plain refs;
- `Abella_driver.compiling := []` clears cycle detection;
- `Output.collect_mode ()` resets the message buffer.

The source-import sandbox saves and restores the same set around its
sub-session; only the generated `.thc` is deliberately added to the
virtual FS on success. `Unify.local_used` is per-call scratch and needs
no restore, and `Prover.built_ins_done` is set once at startup.

Worker termination remains the strongest reset and is what the UI uses
for "Stop" and for edits that arrive while a request is running.

#### Multi-file UI model

The project is a flat map of project-relative paths to text. The UI
needs:

- a file sidebar grouped by `.sig`, `.mod`, `.thm`, with the root
  reasoning file marked;
- select a file to edit it in the main CodeMirror pane;
- "add file" / "rename" / "delete" for scratch projects;
- a "set as root" action for `.thm` files;
- all files editable in v1; imported modules are recompiled on demand
  when they or their dependencies change;
- an edit to any spec file, imported module, or file set resets the
  prover session; edits to the root `.thm` use incremental rewind.

For a web-like default, the sidebar can be collapsed so the page still
looks like "Signature/Module + Reasoning + Trace".

### 5.8 Phase 0 bake-off: js_of_ocaml vs wasm_of_ocaml (complete)

**Result: wasm_of_ocaml selected.** Both backends were built from the
same `src/js/abella_js.ml` and exercised through the same classic-worker
protocol. wasm passed every correctness gate and was consistently about
2× faster; artifact size is comparable.

WasmGC and Wasm tail calls became Baseline in December 2024. The wasm
floor is Chrome/Edge 119+, Firefox 122+, and Safari 18.2+; js_of_ocaml
has the broader floor. Node.js 22+ is needed if the wasm output is run
outside a browser.

#### Environment

- OCaml 5.5.1 (flambda), Dune 3.24.2, Debian trixie.
- js_of_ocaml / js_of_ocaml-ppx / wasm_of_ocaml-compiler **6.4.1**;
  system Binaryen **120** (`wasm-opt`).
- Chromium 150.0.7871.181 (headless), Playwright Firefox 157.0.
- Intel Core Ultra 7 165H, 30 GB RAM.
- `dune build --profile release`; medians of five runs per measurement.
- Node 20.19.2 could not run the wasm output (it lacks the required
  `stringref`/GC feature set by default), so browser numbers are
  authoritative; Node 22+ is needed for CLI wasm tests.

#### Correctness gates (passed on both backends)

- The classic worker starts and exposes `globalThis.Abellajs`.
- `Js.Unsafe.callback` / `init` / `process` / `back` round-trips work.
- `State.snapshot` / `State.reload` / `State.Undo`, including the
  `Weak`-based `State.rref` implementation, work across reset and
  rewind.
- A small proof and the import-heavy CCS development process.
- Source import and generated `.thc` round-trip via
  `Marshal.to_string` / `Marshal.from_string`.
- A missing virtual file produces a clean Abella error
  (`Opening: ./nope.thm`), not a runtime crash.
- The JS launcher + `.wasm` assets load correctly in a worker.
- Chromium 150 and Firefox 157 run both engines. Safari 18.2+ could not
  be tested on Linux; the documented floor remains.

`.thc` comparison: the four compiled values from the generated `.thc`
were structurally equal to native `abella -c` output for both a tiny
module and `ccs_core`, on both engines. For the tiny module, the wasm
bytes also matched native byte-for-byte (516 B); js_of_ocaml produced
498 B because the empty spec signature marshals differently. This is
expected and harmless: each runtime only reads bytes it generated, and
the semantic values match.

#### Performance (median of 5, Chromium 150, release build, ms)

| Measurement | js_of_ocaml | wasm_of_ocaml |
| --- | ---: | ---: |
| Worker startup, small project | 36.1 | 32.5 |
| First import, source-compiled (tiny) | 12.8 | 6.7 |
| Generated `.thc` reload (tiny) | 0.5 | 0.2 |
| `theorem` / `intros` / `search` (tiny) | 0.7 / 0.8 / 0.6 | 0.2 / 0.4 / 0.4 |
| Whole tiny-project sequence | 61.0 | 46.6 |
| Worker startup, CCS | 37.4 | 32.8 |
| `ccs_core` source compile (9.8 KB `.thc`) | 126.3 | 45.8 |
| `ccs_core` `.thc` reload | 1.4 | 0.6 |
| `ccs_bisim` source import | 79.8 | 36.3 |
| `ccs_ctx` source import | 864.2 | 360.5 |
| `ccs_bisim_examples_helper` source import | 227.4 | 103.5 |
| Fixed proof sequence (`coinduction` … `search`) | 10.0 | 5.1 |
| Whole CCS benchmark | 1352.7 | 588.1 |

Artifact size (release):

| Artifact | Raw | Gzip |
| --- | ---: | ---: |
| js_of_ocaml single JS file | 657 KB | 144 KB |
| wasm launcher + `.wasm` assets | 552 KB | 159 KB |

The unminified development build is 9.6 MB for js_of_ocaml and 65 KB +
1.75 MB for wasm (5.5 MB including source maps).

Memory: whole-Chromium RSS after the CCS run was 742 MB (js) and 723 MB
(wasm); this is coarse and dominated by the browser baseline. Worker
`performance.memory` is not exposed, so a precise engine-heap comparison
was not possible. No memory problem was observed.

#### Deployment checks (wasm)

- The server **must** send `application/wasm`; with
  `application/octet-stream`, `instantiateStreaming` fails with
  "Incorrect response MIME type".
- The CSP **must** include `'wasm-unsafe-eval'` in `script-src`;
  without it, instantiation fails. js_of_ocaml runs under
  `script-src 'self'` with no eval permission.
- Asset URLs resolve relative to the **worker** script URL. A worker at
  `web/abella_worker.js` that imports `web/abella_js/...` looks for
  `web/abella_js.bc.wasm.assets/` and gets a 404. The wasm worker
  bootstrap must therefore live at `web/abella_js/worker.js`, next to
  the launcher and asset directory. The page creates that worker when
  `engine.json` says `wasm`; the js backend keeps
  `new Worker("abella_worker.js")`.
- Required browser floor: Chrome/Edge 119+, Firefox 122+, Safari 18.2+.

#### Decision

The §5.8 rule gives a clear result: wasm passes every hard gate, is
about **2.3× faster** on the import-heavy benchmark and about **2×**
faster on individual proof commands, and artifact size is comparable
(144 KB vs 159 KB gzipped). **wasm_of_ocaml is the deployed backend.**
js_of_ocaml stays buildable (guarded stanza) for diagnosis and as an
emergency fallback, but is not shipped: one artifact set and one test
matrix are simpler, and the higher wasm browser floor is acceptable.
The cost is Binaryen at build time plus the MIME/CSP requirements above.

The adapter, frontend, and worker protocol do not change between
backends; only `src/js/dune`, build/deploy artifacts, worker bootstrap,
and CSP/MIME configuration differ.

  start to the current processed tip.
- A `StateEffect` replaces the decoration set when the tip moves.
- On document changes, the field maps decorations through
  `tr.changes`; the session controller simultaneously rewinds the
  prover if the edit intersects the processed region.
- A subtle gutter/line marker indicates the tip.

Errors:

- Use `@codemirror/lint`'s `setDiagnostics` with the failing command's
  range and the error message.
- Add `lintGutter()` and clear diagnostics on edit or successful
  processing.

### 6.4 Languages and highlighting

Use `StreamLanguage` from `@codemirror/language`, not a Lezer grammar.
Abella's lexer is small and a stream tokenizer is exactly the right
level of abstraction.

`abella-lang.ts`:

- Keyword list from `src/lexer.mll` (keep a comment pointing at that
  file; optionally generate the list at build time later).
- Token classes:
  - `%`-to-EOL and nested `/* ... */` comments;
  - double-quoted strings;
  - numbers;
  - keywords (top-level and tactic);
  - capitalized identifiers as type/variable names;
  - operators `=>`, `<=`, `:-`, `:=`, `|-`, `->`, `\/`, `/\`, `\`,
    `&`, `::`, `=`, `:`, `*`, `@`, `#`, `+`;
  - punctuation.
- Two modes: `abella` (reasoning) and `lprolog` (sig/mod), with the
  appropriate keyword sets. The differences are small enough to share a
  tokenizer with a keyword table parameter.
- `HighlightStyle` maps tags to CSS classes so the page theme can change
  without touching the editor code.

Autocomplete (tactic names, hypothesis names) is out of scope for v1;
the CodeMirror `autocompletion` package can be added later.

### 6.5 Command scanner (`commands.ts`)

The scanner is the frontend equivalent of the old Ace token walk. It
must correctly handle:

- `% ...` line comments,
- `%:name:` clause-name markers,
- nested `/* ... */` comments,
- `"..."` strings with no escapes,
- `.` as a terminator only outside comments/strings,
- `#back.` / `#reset.` (recognized as commands but the UI does not need
  to send them in normal use),
- multi-line commands.

Interface:

```ts
interface Command {
  text: string;   // trimmed command without the trailing dot? include dot
  from: number;   // document offset of first non-space char
  to: number;     // offset just after the terminating dot
  endLine: number;
}

scanCommands(doc: string, fromOffset: number): Command[]
```

The scanner returns complete commands from `fromOffset` to EOF; the
session controller semantics are:

- `Ctrl/Cmd-Enter` checks commands with `command.from < cursor`. A
  command at the cursor's first character is **not** checked; a command
  the cursor is inside is checked as a whole.
- If the cursor is already before the checked tip, Ctrl-Enter rewinds to
  the last command whose `to <= cursor` and stops; a second press
  advances again.
- There is no blocking mode and no `Ctrl/Cmd-Shift-Enter`.
- `Ctrl-]` checks the next unchecked command; `Ctrl-[` unchecks the last
  checked command. They move the cursor only when it was at the checked
  tip.
- `Ctrl-.` moves the cursor to the checked tip and scrolls it into view.

Scanning can stop early once the controller has enough commands.

The scanner should throw a descriptive error for unclosed comments or
strings; the session controller surfaces it as a diagnostic. It works in
CodeMirror/JS offsets. Separately, compute UTF-8 byte offsets for the
`SourcePos` sent to Abella (line starts can be cached per document
version). Abella's returned ranges are byte-based and are not used as
editor offsets.

### 6.6 Session controller (`session.ts`)

State:

```ts
interface ProjectTextFile {
  text: string;
  kind: "abella" | "text";        // text files are ignored by the prover
}

interface Project {
  files: Map<string, ProjectTextFile>;
  root: string;                   // path of the root .thm
  sigPath?: string;               // root .sig path used by the bundle
  modPath?: string;               // root .mod path
}

interface Step {
  from: number;
  to: number;
  tip: number;          // offset after the command, usually `to`
  theorem?: string;
  startState?: ProofState;
  endState?: ProofState;
}

class Session {
  driver: Driver;                 // async facade
  project: Project;
  steps: Step[];
  tip: number;                    // first unprocessed offset in root
  dirty: boolean;                 // project/spec changed since init
  status: "idle" | "processing" | "compiling" | "ok" | "error";
}
```

Operations:

- `init(project)`: call driver `init(files, root)`, clear steps/tip/trace.
  Only `kind: "abella"` files are sent to the worker; `kind: "text"`
  files stay in the main-thread project and are included in zip/save
  operations.
- `processTo(cursor)`: ensure initialized (and initialized
  against the current project); scan commands from `tip` to `cursor`;
  process each sequentially; stop on the first error.
- `processAll()`: scan to end of root and process all commands.
- `rewindTo(offset)`:
  - if `offset >= tip`, do nothing;
  - find the first step whose `from <= offset < to` (edit inside a
    processed command) or `from >= offset` (edit before it);
  - call `driver.back(steps.length - index)` (skip the call when the
    count is zero);
  - drop those steps and set `tip = steps[index].from`.
- `onDocChange(update)`:
  - if the edit is in the root `.thm` and the minimum `fromA`/`fromB`
    is `< tip`, schedule `rewindTo(minFrom)`;
  - if the edit is in the root `.sig`/`.mod`, an imported module, or a
    newly added/renamed/deleted file, set `dirty` and clear processed
    decorations/trace (or defer until the next process);
  - editing an imported `.thm` resets the session (clearing the
    virtual-FS `.thc` cache); it cannot rewind incrementally because the
    imported module's proof state is not part of the root's step list;
  - editing a `kind: "text"` file only updates the project and
    persistence; it never resets the prover.
- `reset()`: `driver.reset(project, ...)`, clear steps/tip/trace. The
  driver call includes the Abella files and root; text files are not sent
  to the worker.
- `setProject(project)`: replace the project, mark dirty, re-init before
  the next process.

Concurrency:

- serialize requests through a promise queue;
- disable Process buttons while a request is in flight (editing remains
  possible);
- if a spec/imported-file edit arrives while a request is in flight,
  terminate the worker and reset after the current request is rejected;
- yield to the browser between commands (`requestAnimationFrame` or
  `setTimeout(0)`) so the UI can repaint;
- show a distinct "compiling imported module…" status while source
  compilation runs.

Loading an example or starting from scratch calls `init` and clears the
editor history via CodeMirror's `history` compartment or
`EditorState` reset.

### 6.7 Trace rendering (`trace.ts`)

Types mirroring `Output`:

```ts
type RawMessage =
  | { type: "top_command"; id: number; command: string; range?: number[] }
  | { type: "proof_command"; id: number; thm_id: number; theorem: string;
      command: string; start_state: ProofState; end_state?: ProofState;
      range?: number[] }
  | { type: "system_message"; id: number;
      severity: "info" | "error"; message: string }
  | { type: "link"; id: number; source: number[]; url: string };

interface ProofState {
  name: string;
  vars: [string, string | null][];
  hyps: [string, string][];
  goal: string;
  more: number;
}
```

Rendering rules:

- Build DOM nodes; use `textContent` for system messages and hyp/goal
  text, and a small escaping helper for the sequent renderer. Never pass
  raw Abella output to `innerHTML`.
- The goal panel renders the latest state with the existing
  `sequentToString` logic (variables, hypotheses, separator, goal, and
  "+ N more subgoals").
- The message panel appends one row per `system_message`, with a
  `data-severity` attribute for styling.
- `link` messages are ignored in the interactive page (they point at
  generated `.lp.html` files that do not exist in this context).
- On failure, highlight the failing command range and show the error.
- For a command that emits many messages, keep the transcript ordered as
  emitted by `drain` (chronological).

Reuse strategy: extract `makeSafe`, `bg`, `SequentObj`,
`sequentToString`, and the syntax regexes from `support/ts/abella_doc.ts`
into a shared `support/ts/lib/trace.ts`, and import them from both
`abella_doc.ts` and the web renderer. This avoids two divergent
renderers. If extraction threatens the doc build, duplicate the small
renderer for v1 and note the follow-up.

## 7. Examples and persistence

### 7.1 Curated multi-file examples

The curated bundle currently contains:

- `type-uniq` (single spec, no imports) — baseline;
- `stlc-weak-norm` (specification and imports);
- `hh_meta` (single file);
- `first-order/lists` and `compute/nats` (small examples);
- `programming-languages/howe` (imports `sim` and `subst`) — replaces
  CCS in the bundle because the full CCS development is needlessly slow
  for a default example;
- `process-calculi/pic/pic_bisim_examples` (imports π-calculus modules);
- `misc/umt` (single file).

The legacy branch's examples remain a fallback for examples that no
longer load standalone, but they should not be copied wholesale; current
examples are the source of truth.

Bundle format (`web/examples/bundle.json`) — text only:

```json
{
  "version": 1,
  "examples": [
    {
      "id": "howe",
      "group": "Programming languages",
      "name": "Howe's congruence",
      "root": "examples/programming-languages/howe/howe.thm",
      "sig": "examples/programming-languages/howe/pclf.sig",
      "mod": "examples/programming-languages/howe/pclf.mod",
      "files": [
        "examples/programming-languages/howe/howe.thm",
        "examples/programming-languages/howe/sim.thm",
        "examples/programming-languages/howe/subst.thm"
      ]
    }
  ],
  "files": {
    "examples/programming-languages/howe/howe.thm": "Specification \"pclf\"....",
    "examples/programming-languages/howe/pclf.sig": "..."
  }
}
```

Each example carries its own transitive file list; the client loads only
those files so unrelated examples do not appear in the project pane.
`sig`/`mod` are optional: some examples (Howe, π-calculus) use a
`Specification`; others declare `Kind`/`Type` inline. The UI shows only
the files that exist.

Generation steps:

1. Use `Depend.thm_dependencies` to compute the transitive `.thm`
   import graph and the spec `.sig`/`.mod` dependencies for each curated
   root.
2. Read all text files and emit `bundle.json`. Do not include `.thc` or
   binary data.
3. The frontend fetches `bundle.json` and registers the text files in
   the virtual project. If the example directory contains READMEs or
   other small text files, include them as non-Abella project files.

Use a new native `src/abella_bundle.ml` executable that reuses
`Depend.thm_dependencies`. A Node script would have to re-implement
Abella's dependency syntax; the OCaml tool is small and authoritative.
It should take a small curated-example manifest (name, group, root
`.thm`) and an output path. It is a build tool, not part of the installed
user-facing binaries.

On a fresh load, imported modules are compiled from source the first
time they are encountered; the generated `.thc` is cached for the rest of
the session. Large examples (CCS, π) will be slow on first use; show
progress. Choose a mix of small and medium examples so the default
experience is responsive.

The frontend fetches the bundle relative to the page. If the page is
opened from `file://`, fetch fails; show a clear message to serve over
HTTP.

A scratch project uses `empty.sig`, `empty.mod`, and `main.thm`; users
can add `.sig`/`.mod`/`.thm` files, set any `.thm` as the root, and
`Import` newly added modules (compiled from source in the worker).
Prefill `main.thm` with `Specification "empty".` so the first
`Ctrl-Enter` has something valid to process.

### 7.2 `localStorage`

Store the whole project as one versioned JSON document:

- `abella.web.v1.project`:
  ```json
  {
    "version": 1,
    "files": {
      "empty.sig": "...",
      "empty.mod": "...",
      "main.thm": "...",
      "README.md": "..."
    },
    "root": "main.thm",
    "active": "main.thm",
    "example": "ccs"
  }
  ```
  Non-Abella text files are stored the same way; their kind is inferred
  from the extension.
- `abella.web.v1.tab` / sidebar state (optional).

Behavior:

- restore the saved project on load; if absent, show a scratch project:
  `sig empty.` / `module empty.` / an empty reasoning file;
- if the saved project records an `example`, fetch that bundle only if
  the saved text is missing (the saved text is authoritative); no `.thc`
  data is stored or fetched;
- loading an example replaces the project with the bundle and resets;
- debounce writes (250 ms); catch quota errors and show a warning;
- "Start from scratch" clears the key and resets the session;
- `.thc` bytes are never stored in `localStorage`; the session cache is
  rebuilt after a reload, and text sources are always stored;
- processed state is never persisted; a reload starts from scratch.

### 7.3 Local filesystem backend (File System Access API, v1 best-effort)

The local-directory backend is **in v1 but strictly timeboxed**: one
implementation round plus one debugging round. If it is not reliably
opening, reading, and writing a folder by then, hide it and ship the zip
fallback. It must never block the prover core, the worker protocol, or
the zip path.

Delivered in Phase 3b and isolated in
`support/ts/web/workspace-directory.ts`. The implementation stayed
inside the timebox: **Open folder**, **Save**, and **Save all** work on
Chromium, dirty files are marked in the sidebar, and permission failures
leave the zip path untouched. IndexedDB "reopen last folder" was
deliberately left out to keep the round small; the folder must be
re-picked after a reload.

The virtual FS remains the interface the prover sees. A local directory
can be layered underneath it on Chromium-based browsers:

- feature-detect `window.showDirectoryPicker`;
- `showDirectoryPicker({ mode: "readwrite" })` from a user gesture;
- recursively read the chosen directory, mapping files to
  project-relative paths;
- include `.sig`, `.mod`, `.thm`, and small text files such as
  `README.md`, `LICENSE`, and `NOTES.txt`; skip `.git`, `node_modules`,
  `_build`, hidden directories, binaries, and files above a size/count
  limit (512 KiB per file, 500 files, eight directory levels);
- choose the root from a `project.json` `root`, then a sole `.thm`,
  then `main.thm`, then `<folder>.thm`, then the first `.thm` by path;
- write changed files with `FileSystemFileHandle.createWritable()`;
- re-pick the folder each session; an IndexedDB handle store is a later
  addition;
- check `queryPermission`/`requestPermission` and show actionable
  errors;
- track dirty files and offer **Save** / **Save all**;
- detect external modification via `getFile().lastModified` and warn
  before overwriting (best-effort; must not block the feature);
- disable **+ File**, **Rename**, and **Delete** while a folder is open;
  use the system file manager for structural changes, and **Set root**
  remains available in the app;
- do not write `.thc` files: the `.thc` cache stays in the worker's
  virtual FS for the session (keeps the binary-hash problem out of the
  user's directory).

The picker APIs are main-thread-only. The main thread reads/writes the
directory; the worker only receives the project map. This preserves the
same worker protocol as the virtual backend.

Browser support and fallback:

- Chromium desktop supports the API; Firefox and Safari do not (as of
  this plan). Android support is limited.
- If `showDirectoryPicker` is unavailable, permission fails, or the
  timebox expires, hide **Open folder** and use the standard
  **Import zip** / **Download zip** flow (`fflate`).
- A read-only `<input type="file" webkitdirectory>` fallback can load a
  folder in browsers without the picker API; saving then uses the zip
  export.
- Never access the filesystem without an explicit user gesture and
  permission prompt.

### 7.4 Remote git forges and Dropbox (later phases)

The best-case workflow — load a git repository, edit, click **Commit** —
is feasible with provider REST APIs, but it is a separate feature with
authentication and conflict handling. It should not be part of the
initial prover UI milestone.

#### Workspace abstraction

```ts
type WorkspaceKind =
  | "virtual"
  | "memory"
  | "directory"
  | "site"
  | "github"
  | "gitlab"
  | "gitea"
  | "dropbox";

interface WorkspaceCapabilities {
  write: boolean;
  remove: boolean;
  structural: boolean; // create/rename/delete in the app
  refresh: boolean;
  commit: boolean;
  autoSave: boolean; // virtual projects persist automatically
}

interface Workspace {
  kind: WorkspaceKind;
  name: string;
  capabilities: WorkspaceCapabilities;
  list(): Promise<FileEntry[]>;
  read(path: string): Promise<string>;
  write(path: string, text: string): Promise<void>;
  remove?(path: string): Promise<void>;
  refresh?(): Promise<void>;
  commit?(message: string): Promise<CommitResult>;
  baseRevision?: string;
  close?(): void;
}
```

The in-memory project map remains the authoritative content model. A
`Workspace` is I/O only, and a new `WorkspaceSession` owns the active
backend, capabilities, dirty state, save/save-all/commit operations, and
backend switching. Workspaces never own or mutate the project map
directly.

Workspace paths are project-relative POSIX paths. The model is
text-only: `.thm`, `.sig`, `.mod`, and allow-listed small text files.
Generated `.thc` files stay inside the worker's virtual filesystem and
are never read from or written to a workspace.

Capabilities drive the UI. `write` controls Save/Save all,
`structural` controls create/rename/delete, `refresh` controls
re-read/reconnect, and `commit` controls remote commit. Optional methods
must fail explicitly when invoked without the corresponding capability.

Workspace failures use a typed code rather than raw platform errors:

```ts
type WorkspaceErrorCode =
  | "cancelled"
  | "permission-denied"
  | "not-found"
  | "unsupported"
  | "conflict"
  | "unavailable"
  | "io";
```

The optional commit types are defined now but are not implemented until
Phase 6:

```ts
type CommitResult =
  | { status: "committed"; revision: string }
  | { status: "conflict"; message: string };
```

Backend selection lives in a compact topbar workspace control showing
the active backend and name. Virtual and directory backends are
implemented in Phase 5; `site` and remote providers follow.

Directory handles are stored in IndexedDB so the last folder can be
reattached after a reload; permission is re-requested on a user gesture.
If reattachment fails or permission is denied, the text snapshot is
restored as a detached read-only copy and zip export remains available.

Browsers without `showDirectoryPicker` use a read-only in-memory
workspace loaded through `<input type="file" webkitdirectory>`. It
shares the directory filters and root heuristic, hides all write
actions, and keeps **Download zip**.

Directory structural actions stay disabled in Phase 5
(`capabilities.structural = false`); virtual projects keep them.

Use standard, browser-capable clients rather than hand-rolling the
provider APIs:

| Provider | Library | Browser | Notes |
| --- | --- | --- | --- |
| GitHub | `@octokit/rest` (Octokit) | yes | Official SDK; REST, pagination, rate-limit/retry plugins, token auth. Use Git Data API for multi-file commits. |
| GitLab | `@gitbeaker/rest` (GitBeaker) | yes | Typed SDK for browsers/Node/Deno; commits API supports multiple file actions in one commit. |
| Codeberg/Gitea | `gitea-js` | yes | Generated from Gitea's OpenAPI; fetch-based; PAT auth. Large; lazy-load. CORS is instance-configurable; verify Codeberg before committing. |
| Dropbox | `dropbox` (official SDK) | yes, incl. workers | Files list/download/upload; PKCE support via Web Crypto. No git semantics. |
| OAuth/PKCE | `oauth4webapi` | yes | Low-level OAuth 2.1/OIDC client; PKCE and device flow; zero dependencies. |
| ZIP fallback | `fflate` | yes | Import/export local projects. |

All of these are MIT-licensed and are standard clients/utilities, not UI
frameworks. Load each provider client only when that backend is selected;
do not put Octokit/GitBeaker/Dropbox in the initial page bundle.

`isomorphic-git` is a capable browser git implementation, but pushing to
many forges requires a CORS proxy because their git smart-HTTP endpoints
are not CORS-enabled. That conflicts with a fully static deployment, so
it is not the default. It could be revisited for local-only git history.

The app does not attempt merges: commits are fast-forward only, and a
moved remote ref aborts with a "reload" message.

#### GitHub (first backend)

Use `@octokit/rest`:

- Read: `octokit.rest.repos.get`, then
  `octokit.rest.git.getTree({ recursive: "1" })`; keep `.sig`/`.mod`/
  `.thm` blobs plus small text files (README, LICENSE, etc.); skip
  binaries and oversized files. Fetch contents with `getBlob` or raw
  URLs. Public repos are readable without a token (read-only); writes
  always require a token.
- Write: Git Data API — `git.getRef`, `git.createBlob` per changed file,
  `git.createTree` with `base_tree`, `git.createCommit`,
  `git.updateRef` with `force: false`. One commit for all changed files.
- Auth: fine-grained PAT or the GitHub OAuth popup; see the
  authentication section below.
- Rate limits: 60 requests/hour unauthenticated, 5,000/hour with a
  token; `@octokit/plugin-throttling` and `@octokit/plugin-retry` are
  available if needed.
- Conflict: a non-fast-forward ref update (HTTP 422) prompts the user to
  reload the remote state; no automatic retry loop.

#### GitHub authentication (PAT or OAuth)

“Public repository” means **publicly readable**, not publicly writable.
Separate visibility from access mode:

| Scenario | Token needed | Permissions |
| --- | --- | --- |
| Public repo, read-only | No (optional for higher rate limits) | — |
| Private repo, read | Yes | Fine-grained `Contents: Read` |
| Public repo, write | Yes | `Contents: Read and write`; user must have push access |
| Private repo, write | Yes | `Contents: Read and write`; user must have push access |

- A token never grants access beyond the user's own repository
  permissions.
- Public unauthenticated reads are limited to 60 API requests/hour per
  IP; a token raises this to 5,000/hour. Large public repos may
  therefore still want a token for reading.
- Fine-grained PATs are scoped to selected repositories and permissions.
  The UI links to GitHub's fine-grained token page and explains that
  `Contents: Read and write` is required for commits, `Contents: Read`
  for private reads.
- UX: **Load public repo** needs no token and is read-only. **Connect
  GitHub** opens a dialog: create/paste a token, validate with
  `GET /user` and `GET /repos/{owner}/{repo}`, show the account and repo
  access, and offer **Disconnect**. If a public read-only project later
  clicks **Commit**, prompt for a token at that point and resume.
- The same dialog offers **Sign in with GitHub**:
  1. the main tab generates `state` and a PKCE S256 verifier/challenge;
  2. a popup opens GitHub's authorization page;
  3. GitHub redirects to the static `web/github-callback.html` page;
  4. the callback posts only `code` and `state` to the opener and removes
     them from its URL;
  5. the main tab verifies origin, source, and state, then sends the code
     and verifier to a small Cloudflare Worker;
  6. the Worker exchanges the code using the client secret and returns
     only `token` and `scope`;
  7. the main tab validates the token with `GET /user`, stores it in
     `sessionStorage`, and hands it to the existing workspace path.
- The Worker at `oauth.abella-prover.org` is the only component with the
  client secret. It allows only the exact site origin, fixes the
  redirect URI, caps request bodies at 4 KiB, times out upstream calls,
  does not follow redirects, and logs no code, verifier, token, or
  secret. Its `/github/config` route is the availability flag: when it is
  missing or rejects the origin, the UI hides OAuth and keeps the PAT
  path.
- `public_repo` is the default OAuth scope. `repo` is an explicit,
  account-wide opt-in; a fine-grained PAT remains the least-privilege
  path for selected repositories.
- The OAuth token and a PAT are both ordinary bearer tokens for Octokit.
  Store the token in `sessionStorage` (never `localStorage`), clear it on
  disconnect/tab close, and never log or include it in error text. The
  granted scope and account login may be kept in a separate session key.
- If GitHub returns 401, clear the token and prompt again. A 403 means
  insufficient token permissions or no push access to the repo; do not
  treat it as an expired token.
- Signing in does not require a repository first. Once a token is saved,
  the primary dialog action is **Load repository** (or **Authorize
  commit**), and the OAuth action becomes **Reconnect with GitHub**.
- Device flow and a GitHub App remain future alternatives: device flow
  needs no secret but requires copying a code into GitHub; a GitHub App
  would provide repository-scoped permissions and a different exchange.

This is the recommended first remote backend: Octokit is mature, public
repos can be loaded without auth, and the write path is a single
well-documented Git Data API flow.

#### GitLab

Use `@gitbeaker/rest`:

- Read: `api.Repositories.allRepositoryTrees` and `api.RepositoryFiles.showRaw`.
- Write: `api.Commits.create` with a list of `actions`
  (`create`/`update`/`delete`) — one commit for all changes, simpler
  than GitHub.
- Auth: `new Gitlab({ host, token })`; GitLab supports OAuth PKCE, so a
  static client can use `oauth4webapi` later. A PAT is the simpler v1
  fallback.

#### Codeberg / Gitea / Forgejo

Use `gitea-js`:

- Read: the generated repository contents/tree methods.
- Write: the contents API. Multiple changed files may require multiple
  commits unless the instance exposes a multi-file commit endpoint;
  label the result accordingly rather than pretending it is atomic.
- Auth: `giteaApi(host, { token })`; PAT first, OAuth where available.
- The generated client is large; lazy-load it and check Forgejo
  compatibility against the Gitea API version.
- **CORS caveat:** Gitea's CORS support is instance-configurable and may
  be disabled or limited to `/api`; raw content endpoints may not send
  CORS headers. Verify against `codeberg.org` early. If it is not
  usable from a static origin, skip this backend rather than adding a
  proxy.

#### Dropbox

Use the official `dropbox` SDK:

- `filesListFolder`, `filesDownload`, `filesUpload` /
  `filesUploadSession*`.
- Dropbox is not a git forge. "Commit" becomes **Save snapshot**; there
  is no commit graph, only file revisions.
- The SDK supports browser PKCE via Web Crypto; use
  `new Dropbox({ accessToken })`. Keep tokens in memory/`sessionStorage`.
- Verify CORS support for the endpoints used; otherwise fall back to
  zip export/import.

#### Authentication and security

- No client secrets in static assets.
- **First remote backend (GitHub): PAT or OAuth popup.** The PAT path
  needs no app registration; the user creates a fine-grained token and
  pastes it. The token acts as that user and never grants more than their
  repository permissions.
- The OAuth path uses a GitHub OAuth App, the static
  `web/github-callback.html` relay, and a small Cloudflare Worker at
  `oauth.abella-prover.org`. PKCE protects the authorization code, but
  GitHub's web-flow token exchange still requires the client secret, so
  the Worker is required. The Worker stores nothing and returns only
  `token` and `scope`.
- Later providers may use OAuth PKCE (GitLab, Gitea, Dropbox) via
  `oauth4webapi` or the provider SDK. GitHub device flow and a GitHub App
  remain future alternatives.
- Do **not** build a full-page redirect OAuth flow for the static site:
  it would unload the prover, editor, unsaved edits, and pending commit.
  The GitHub flow is a popup.
- Store tokens in memory or `sessionStorage`, clear on tab close, use
  minimal scopes/permissions, and never include them in error messages
  or logs.
- A strict CSP is important because a token compromise via XSS is worse
  than a lost proof session.
- Show the account/repo being written to before the first commit.

#### Load and commit UX

- **Load**: a dialog accepts a repo URL or `owner/repo`, branch, and
  optional subdirectory. Parse the provider from the host; list files;
  let the user choose the root `.thm`; show a "remote" badge and the
  base commit.
- **Commit**: show changed files and a summary, require a message,
  create one commit where the provider supports it, update the base
  revision, and link to the new commit.
- **Conflicts**: abort and ask the user to reload; no merge UI.
- **Offline/blocked**: always keep **Download zip** available.

#### Effort estimate

| Piece | Estimate |
| --- | --- |
| Local directory backend + permissions + save | 2–3 days |
| Zip import/export fallback | 1–2 days |
| Provider abstraction + GitHub read | 2–3 days |
| GitHub commit + PAT + conflict handling | 3–4 days |
| GitLab read/write + OAuth PKCE | 3–4 days |
| Codeberg/Gitea read/write | 2–3 days |
| Dropbox read/write | 1–2 days |
| Auth/security polish, tests | 3–5 days |

A solid local-filesystem backend is a few days. A polished multi-provider
git commit feature is roughly **2–3 additional weeks** and should be
planned as Phases 5–6, not as part of the prover MVP.

Recommended sequencing:

1. **Local directory** (Phase 5) first. It validates the workspace UX —
   file tree, dirty state, save/save-all, conflict warnings — with no
   authentication at all.
2. **GitHub read-only** (Phase 6a) next. A public repo can be loaded
   with Octokit and no token; this validates the remote UX.
3. **GitHub commit with a PAT** (Phase 6a). Adds auth, commit message,
   success/conflict states.
4. **Then evaluate.** GitHub is the best first remote backend because
   Octokit is mature, public reads need no auth, and the Git Data API is
   well documented. GitLab is the next easiest: GitBeaker is solid, its
   API supports CORS for `/api`, and its commits API takes multiple file
   actions in one call. Codeberg/Gitea has an uncertain CORS story and
   should be verified before any implementation. Dropbox has different
   (non-git) semantics and can wait.

The delta from GitHub to GitLab is not trivial (different API, auth
options, and commit semantics), but it is much smaller than going from
zero to the first remote backend.

### 7.5 Project interchange and `abella_doc` integration

#### Zip download/import (v1)

Every project gets **Download zip** and **Import zip** actions:

- use `fflate` to create/read the archive;
- include every text file (`.sig`, `.mod`, `.thm`, README, notes, etc.);
- include a `project.json` manifest with `version`, `root`, and the file
  list;
- exclude generated `.thc` caches and other build artifacts;
- import replaces the current project (with confirmation if it is
  dirty), restores the root, and resets the prover session.

The zip is also the fallback path for browsers without the File System
Access API and for remote providers that cannot be used from a static
origin.

#### `abella_doc` “Edit this” (v1.1/v2)

`abella_doc` already computes the dependency graph with
`Depend.thm_dependencies`. Extend it to emit a small manifest next to each
generated theorem page:

```json
{
  "version": 1,
  "root": "ccs_bisim_examples.thm",
  "files": [
    "ccs_bisim_examples.thm",
    "ccs_core.thm",
    "ccs.sig",
    "ccs.mod"
  ]
}
```

The page gets an **Edit this** button linking to:

```
https://abella-prover.org/web/?project=<same-origin-manifest-url>
```

The web app adds a `SiteWorkspace` backend that:

- fetches the manifest (same-origin or explicitly allow-listed);
- fetches the listed files;
- selects the root `.thm`;
- resets the prover.

No `.thc` files are needed; imports are compiled from source and cached
in the session. This is deliberately a **later** feature so the core
project/workspace format is stable first. It is low-risk and high-value:
the doc site becomes an entry point into the interactive editor.

Security: do not let `?project=` fetch arbitrary cross-origin URLs. Keep
it same-origin by default, or allow only an explicit host allow-list.

#### Web → `abella_doc` export (not planned)

Producing `abella_doc`-style pages from the web interface is **out of
scope** until users ask for it. The live UI has the JSON trace, but a
full doc page needs annotated source, proof blocks, hover/focus UI, and
per-file pages for imported modules. That duplicates the `abella_doc`
renderer and requires tracing dependencies, not just compiling them.

If the demand appears, the narrow version is a single-file
**“Export annotated HTML”** snapshot using the existing
`support/ts/abella_doc.ts` renderer. Full multi-file doc parity is not
recommended.

## 8. Keyboard and status UX

- `Ctrl/Cmd-Enter`: set the checked region to the cursor in the root
  file: advance with `command.from < cursor`, or rewind to the last
  command ending at or before the cursor if the cursor is inside the
  checked region.
- `Ctrl-]` / `Ctrl-[`: check the next unchecked command / uncheck the
  last checked command. The cursor moves to the command end/start only
  when the cursor was at the checked tip.
- `Ctrl-.`: move the cursor to the checked tip and scroll it into view.
- `Ctrl/Cmd-Enter` inside an imported module: show a hint that the root
  reasoning file is operated on; edits to imported modules take effect on
  the next root run.
- `Ctrl/Cmd-Z` / `Shift-Ctrl/Cmd-Z`: CodeMirror text undo/redo; the
  session controller detects the resulting document change and rewinds
  the prover appropriately.
- Toolbar: **Process to cursor**, **Process full**, **Reset**,
  **Stop**, **Download zip**, **Import zip**. The sidebar has **+ File**,
  **Rename**, **Delete**, and **Set root**; local folder and remote
  workspace actions appear only on supported/configured backends.
- Status badge:
  - "Ready" (idle),
  - "Processing…",
  - "N commands processed",
  - "Error" (with the failing command highlighted).
- Stop terminates the worker; the next action restarts it and reinitializes
  the project.
- After processing, scroll the goal panel into view on narrow screens.
- Project files can be added, renamed, deleted, and marked as the root
  `.thm`; file operations that affect Abella sources reset the prover.

## 9. Build, dev, and deployment

### 9.1 Make targets

```
make web              # build everything for web/ with ENGINE (default: wasm)
make web ENGINE=wasm  # build the wasm backend
make web ENGINE=js    # build the js_of_ocaml diagnostic/fallback backend
make web-bundle       # regenerate web/examples/bundle.json
make publish-web      # later: make web, then rsync web/ to the site
```

`make web`:

1. check the selected backend's OCaml packages and fail with a helpful
   message:
   - js: `js_of_ocaml js_of_ocaml-ppx`
   - wasm: `wasm_of_ocaml-compiler` plus Binaryen 119+
2. build `src/abella_bundle.exe` and generate
   `web/examples/bundle.json` from `support/web-examples.json`.
3. `cd support && npm install --no-save` and `npm run web:build`
   (main bundle, wasm/js worker bootstraps, CSS).
4. build the selected engine:
   - js: `dune build --profile release src/js/abella_js.bc.js`, copy to
     `web/abella_js.js`
   - wasm: `dune build --profile release src/js/abella_js.bc.wasm.js`,
     copy the launcher and its `.wasm` assets to `web/abella_js/`
5. write `web/engine.json` (`{"engine":"wasm"}` or `{"engine":"js"}`).

Use `--profile release` for deployment: it minifies the js_of_ocaml
output (9.6 MB development → 657 KB release) and the wasm artifacts.

The frontend reads the selected backend from `web/engine.json` and
creates `abella_js/worker.js` or `abella_worker.js` accordingly.

`make all` must **not** require js_of_ocaml, wasm_of_ocaml, Binaryen, or
Node. Keep the web build a separate target. No `.thc` generation is
needed at build time.

### 9.2 Deployment

`web/index.html` references only relative assets:

```html
<link rel="stylesheet" href="abella_web.css">
<script type="module" src="abella_web.js"></script>
```

The worker loads the chosen engine:

- js_of_ocaml: `web/abella_worker.js` does
  `importScripts("abella_js.js")`;
- wasm_of_ocaml (deployed): `web/abella_js/worker.js` does
  `importScripts("abella_js.bc.wasm.js")`. The worker **must** live in
  `web/abella_js/` because the generated launcher resolves its
  `abella_js.bc.wasm.assets/` directory relative to the worker script
  URL. A top-level worker cannot reach those assets (Phase 0 check).

The main bundle selects the worker from `engine.json`:
`new Worker("abella_js/worker.js")` for wasm, or
`new Worker("abella_worker.js")` for js. Both workers speak the same
protocol.

`make publish-web` mirrors the old `publish-doc` style:

```
rsync -aviz web/ abellaweb@abella-prover.org:abella-prover.org/web/
```

Exclude source maps if any; include `examples/bundle.json`,
`engine.json`, `abella_web.js`, `abella_worker.js`, `abella_web.css`,
`workspaces/*.js`, `index.html`, and the logo, plus either
`abella_js.js` or `abella_js/`.

For wasm deployments (selected):

- serve `.wasm` as `application/wasm`; any other MIME type makes
  `instantiateStreaming` fail;
- include `'wasm-unsafe-eval'` in the CSP `script-src`; without it,
  module instantiation is blocked (Phase 0 check). js_of_ocaml only
  needs `'self'`;
- document the browser floor (Chrome/Edge 119+, Firefox 122+,
  Safari 18.2+).

### 9.3 CI

`.github/workflows/web.yml` builds the selected wasm backend and checks
the web frontend:

- install npm dependencies with `npm ci`;
- install Dune, `js_of_ocaml`, and `wasm_of_ocaml-compiler` from opam,
  with Binaryen 120 downloaded explicitly;
- run `npm run check` (TypeScript) and `npm run web:test`;
- run `make web ENGINE=wasm` from a clean checkout;
- run `npm run web:size` against the generated assets.

A headless Playwright smoke test remains an optional follow-up. The
existing OCaml matrix keeps passing `make all-release` and
`dune runtest` without the web dependencies.

## 10. Scope boundaries (v1)

In scope:

- a multi-file project map (`.sig`, `.mod`, `.thm`);
- arbitrary non-Abella text files (README, Markdown, notes) with a
  CodeMirror pane; the prover ignores them;
- `Specification`, `accum_sig` / `accumulate`, and `Import`;
- in-browser source compilation of imports on first use;
- generated `.thc` files cached in the virtual FS for the session;
- editing any project file, including imported modules;
- top-level commands, definitions, theorems, and proof commands;
- incremental process/rewind/reset on the root `.thm`;
- adding, renaming, and deleting files in scratch projects;
- **Download zip** / **Import zip** with a `project.json` manifest;
- **best-effort local-directory access** on Chromium (Timeboxed; hidden
  with zip fallback if it fails or slips);
- selected curated examples.

Deferred to v1.1/v2:

- `abella_doc` “Edit this” links via a site manifest and `?project=`;
- remote git forges and Dropbox.

Out of scope (explicitly):

- producing `abella_doc`-style output from the web interface; revisit
  only if users ask for it;
- a full git client, merges, or rebase UI;
- compiling a new `.thc` with a shell command;
- persisting recompiled `.thc` across page reloads (the cache is
  in-memory for the session);
- `Set load_path` and other file-system-sensitive commands beyond
  project-relative paths (they may work, but are untested);
- URL sharing or saved sessions;
- autocomplete, hover types, and proof-state diffing.

The v1 project is created in-browser or loaded from the text bundle;
`localStorage` persists it. The `Workspace` abstraction (§7.3–7.4) is
introduced in v1 so local-directory and remote backends can be added
without changing the prover worker protocol.

The main v1 limitation is performance when editing large imported
modules: those modules are rechecked from source in the browser.

## 11. Alternatives considered

### 11.1 Server-backed interactive Abella

A native `abella_server` executable (e.g. Dream/Cohttp) keeps a session
in memory and streams JSON messages over HTTP/WebSocket. Pros: no
js_of_ocaml, full file/import support, native performance. Cons: public
service operations, timeouts, memory limits, security, and deployment
complexity. The frontend work is almost identical, so this remains a
viable fallback if the JS build fails.

### 11.2 WASM via `wasm_of_ocaml`

**Selected by Phase 0.** It is part of the js_of_ocaml project, actively
developed, and measured about 2× faster than js_of_ocaml for Abella's
workload. The costs are a higher browser floor (WasmGC + tail calls:
Chrome/Edge 119+, Firefox 122+, Safari 18.2+), Binaryen at build time, a
JS launcher plus `.wasm` assets, and `'wasm-unsafe-eval'` CSP. `Weak`,
`Marshal`, and JS callbacks all passed the Phase 0 gates.

### 11.3 Text output instead of JSON

Simpler adapter (old `capture_everything` style) but forces the frontend
to parse terminal text for proof states and errors. The JSON annotation
mode already exists and is richer. Prefer JSON.

### 11.4 Keep Ace

CodeMirror 6 is the explicit requirement and is maintained; Ace is
effectively legacy. The old Ace mode files can be used as references
for keyword lists and token classes.

  higher rate limits use a fine-grained PAT or a GitHub OAuth token,
  validated with `/user` and repository access checks.
- Reads use the recursive tree, filter files with the shared workspace
  policy, fetch blobs, choose the root, and record the base commit SHA.
- Commits use the Git Data API: blobs, one tree with `base_tree`, one
  commit, and a non-forced ref update. A moved branch is a conflict and
  is never merged.
- The GitHub dialog loads repositories, stores the token in
  `sessionStorage`, supports Disconnect, and prompts for a write-enabled
  token at commit time when the loaded project was read-only.
- `Sign in with GitHub` uses a popup, PKCE S256, the static
  `web/github-callback.html` relay, and the Cloudflare Worker at
  `oauth.abella-prover.org`. The callback page posts only code and state
  to the opener and never exchanges or stores a token. A 401 from a
  later request clears the token; a 403 is not treated as expiry.
- The dialog does not require a repository before sign-in. Once signed
  in, the primary action is Load repository (or Authorize commit), and
  the OAuth action becomes Reconnect with GitHub. `public_repo` is the
  default scope; `repo` is an explicit account-wide opt-in.
- The topbar shows the GitHub workspace and account, exposes Commit, and
  hides Save/Save all. Add/Rename/Delete remain disabled
  (`structural = false`) in this round.
- The last repository URL is remembered in `localStorage`; the token and
  its scope/account metadata are session-scoped.
- Unit tests cover URL parsing, tree-to-project mapping, commit planning,
  moved-branch conflicts, non-fast-forward conflicts, no-change commits,
  missing tokens, token storage, PKCE, callback parsing, OAuth error
  mapping, and 401 status handling.
- Browser tests cover public load, edit, token prompt, commit,
  sessionStorage persistence, blocked/closed popups, state mismatch,
  saved-token loading, reconnect, and conflict handling. The production
  OAuth public-scope connect and commit round trip succeeded on
  2026-10-23; the test commit was removed.
- The deployed CSP must allow `https://api.github.com`,
  `https://raw.githubusercontent.com`, and
  `https://oauth.abella-prover.org` in `connect-src`, and the main page
  must use COOP `same-origin-allow-popups`. The callback path uses
  `Cache-Control: no-store`, `Referrer-Policy: no-referrer`,
  `X-Frame-Options: DENY`, and a restrictive CSP.
- Production infrastructure: Cloudflare DNS with the apex and `www`
  proxied and mail/ftp/lists DNS-only; a DNS-only origin record for SSH
  publishing; a Worker custom domain at `oauth.abella-prover.org`; a
  5-requests/10-seconds token-route rate limit; and report-only-to-
  enforced security headers.

The GitHub UX is accepted for now. Further provider work can proceed when
justified.

### Phase 6b — other providers (only if justified)

- GitLab via GitBeaker: read/write with a single multi-file commit;
  OAuth PKCE and PAT.
- Codeberg/Gitea via `gitea-js`: read/write; document multi-commit
  behavior.
- Dropbox via the official SDK: list/download/upload snapshots; no git
  semantics.
- Optional later: a GitHub App with repository-scoped permissions, or
  device flow as a no-secret fallback; full git clone/merge is out of
  scope.

## 14. Risks and mitigations

| Risk | Mitigation |
| --- | --- |
| Backend fails with OCaml 5.5 or `unix` | Phase 0 built both on OCaml 5.5.1; both passed; server remains the last resort |
| wasm browser floor excludes older browsers | document Chrome/Edge 119+, Firefox 122+, Safari 18.2+; js_of_ocaml target stays buildable as a fallback |
| wasm `Weak`/`Marshal`/FFI runtime gaps | Passed Phase 0 gates on both engines; js_of_ocaml remains the fallback |
| wasm Marshal is quadratic on large `.thc` output | Measured: `ccs_core` generated 9.8 KB in ~46 ms (wasm) vs ~126 ms (js); not a bottleneck |
| wasm asset loading/CSP/MIME issues | Resolved in Phase 0: `application/wasm`, `'wasm-unsafe-eval'`, worker must live in `web/abella_js/` |
| wasm debugging is harder | keep the js_of_ocaml target for diagnosis; release builds retain source maps |
| Binaryen/Dune version mismatch | Pinned `wasm_of_ocaml-compiler` 6.4.x, Dune >= 3.20, Binaryen 120 tested; CI check |
| `Version.self_digest` crashes JS startup | Made lazy and guarded by `Setup.compiled`; verified in Phase 0 |
| Browser-generated `.thc` serialization is wrong | Passed the Phase 0 round-trip and four-value comparison for a tiny module and `ccs_core` |
| Source-import sandbox leaks or corrupts state | Phase 0 exercised rewind, reset, nested imports, and reset-after-edit; add unit coverage in Phase 1 |
| Import compilation is slow for large examples (CCS ~30s natively) | Source compile once per session, then generated `.thc` cache; measured ~0.36 s for `ccs_ctx` on wasm; progress status |
| Nested imports recompile repeatedly | generated `.thc` in the virtual FS plus the `imported` list |
| Editing an imported module leaves stale compiled state | `init`/reset clears the virtual FS (including all `.thc` files) before reprocessing |
| Compiled bundle is large (multi-MB) | wasm release is 552 KB raw / 159 KB gzip; lazy-load the engine and example text; cache headers |
| Long command freezes the UI | Worker from the start; Stop terminates worker |
| Undo/rewind off by one | driver-level test for `back n`; keep a fake-driver test |
| Command scanner mis-splits commands | dedicated unit tests; mirror `lexer.mll` rules |
| Deep edits map decorations incorrectly | use a `StateField` + `tr.changes`; rewind on intersection |
| XSS from Abella output | `textContent` / strict escape; never `innerHTML` from output |
| Curated examples diverge from current Abella | compile and test each example during Phase 2 |
| Project paths mismatch `Filepath.normalize` | canonicalize virtual keys; test root-level and nested examples |
| Reset leaves stale global state | initial `State.snapshot()` reload; worker termination as a stronger reset |
| File System Access API unavailable/denied or timebox slips | feature detection; hide **Open folder**; zip import/export remains; no core dependency |
| External edits overwrite local files | best-effort `lastModified` check; warn/refresh; never block the feature |
| Remote provider CORS/rate limits | verify per provider; clear errors; PAT rate limits; zip fallback. Gitea/Codeberg CORS is especially uncertain. |
| Provider SDK browser/esbuild resolution | lazy chunks; verify Octokit conditional exports with `moduleResolution: bundler`; smoke-test each chunk |
| GitHub token theft via XSS | `sessionStorage` only, minimal scopes or fine-grained PATs, strict CSP, no third-party scripts, Disconnect clears it |
| Confusing public/private or read/write auth | separate “public read-only” from “Connect GitHub”; write always requires a token; explain 401/403 |
| GitHub OAuth proxy creep | small no-storage Worker; exact CORS, PKCE, fixed redirect URI, rate limit, and PAT fallback; no full-page redirect |
| Remote commit conflict | fast-forward only; abort on moved ref and ask the user to reload |
| Zip export of a large project uses too much memory | size/count limits; `fflate` streaming; warn before huge exports |
| Non-Abella file is huge or binary | skip by size/extension; never send to the prover |
| `?project=` fetches arbitrary URLs | same-origin by default; explicit allow-list only |

## 15. Decisions

Confirmed:

1. **Runtime**: static client-side prover. **wasm_of_ocaml** is the
   deployed backend, selected by the Phase 0 bake-off (§5.8);
   js_of_ocaml remains a guarded, buildable fallback but is not shipped.
2. **Worker**: Web Worker from the first usable milestone.
3. **Scope**: multi-file project map with `Import` support.
4. **Imported-file editing**: imported modules are editable and are
   compiled from source in the browser on first use. The generated
   `.thc` is cached in the virtual FS for the session, so reprocessing
   and re-importing are fast.
5. **Zip interchange**: **Download zip** / **Import zip** are v1
   features, with a `project.json` manifest.
6. **Non-Abella text files**: arbitrary text files (README, Markdown,
   notes) are part of the v1 project model, editable in CodeMirror, and
   ignored by the prover.
7. **`abella_doc` “Edit this”**: deferred to v1.1/v2, via a same-origin
   project manifest and a `?project=` route.
8. **Web → `abella_doc` export**: not planned; revisit only if users ask
   for it.

9. **Trace UI**: live **Goal** panel only, with a collapsed Output
   disclosure. No raw CLI trace and no per-command proof-state history.
   The Goal is primary; proof outcomes appear under the last obligation,
   and warnings/errors/`Show`/`Query` live in Output.
10. **Examples**: current `examples/**`, plus a few small/medium
    examples for quick tests. Legacy examples are only a fallback for
    something that no longer parses.
11. **Page location**: top-level `web/`, served at `/web/`.
12. **Styling**: plain modern CSS with custom properties and nesting,
    built by esbuild. No Tailwind in Abella Web. Tailwind remains only
    for the existing `abella_doc` build. CodeMirror theme is TS and
    shares the same variables.
13. **Backend packaging**: both dune targets are guarded/optional; the
    selected wasm toolchain is documented for `make web`, and neither
    compiler is a mandatory dependency of the native `abella` runtime
    package. The js_of_ocaml target stays buildable for diagnosis and as
    an emergency fallback but is not part of the deployed artifact set.
14. **Local filesystem**: v1 **best-effort**, delivered in Phase 3b
    within the timebox. Feature-detected; if it fails or slips, hide
    **Open folder** and use zip. Never blocks the core. IndexedDB reopen
    is deferred; **Add/Rename/Delete** stay virtual-project actions and
    are disabled while a folder is open.
15. **Remote integration order**: **GitHub only first** (read + PAT or
    OAuth commit via Octokit), then stop and evaluate. GitLab is next if
    justified. Codeberg/Gitea only if its CORS works from a static
    origin. Dropbox is deferred; its non-git “snapshot” semantics are a
    separate UX decision.
16. **Authentication**: fine-grained **PAT** and a GitHub **OAuth
    popup** for GitHub; both tokens stay in `sessionStorage`. Public
    repos are readable without a token. OAuth uses PKCE S256, a static
    callback page, and a small Cloudflare Worker at
    `oauth.abella-prover.org` holding the client secret; `public_repo` is
    the default and `repo` is an explicit account-wide opt-in. PATs
    remain for per-repository least privilege and fallback. Private reads
    need `Contents: Read`; writes need `Contents: Read and write` and
    the user's own push access. Device flow and a GitHub App remain
    future alternatives.
17. **Provider libraries**: Octokit, GitBeaker, `gitea-js`, the official
    Dropbox SDK, and `oauth4webapi` are accepted as standard-task
    libraries; they are lazy-loaded and are not UI frameworks.
18. **Web hardening**: the generated `.thc` session cache is bounded to
    64 MiB with oldest-first eviction; IndexedDB persistence of the
    import cache is deferred. Markdown language support is a lazy chunk,
    and CI enforces deployed asset-size budgets.
19. **Project ownership**: `Project` remains the authoritative in-memory
    content model. `Workspace` is I/O only, and `WorkspaceSession` owns
    the active backend, dirty state, save/commit operations, and
    switching.
20. **Workspace shape**: use a capability object (`write`, `remove`,
    `structural`, `refresh`, `commit`, `autoSave`) plus optional mutation
    methods. Failures use typed workspace error codes. Commit/revision
    types are defined now but not implemented until Phase 6.
21. **Workspace contents**: project-relative POSIX paths, text files
    only. Generated `.thc` files stay in the worker virtual FS.
22. **Saving and persistence**: virtual mode keeps debounced
    `localStorage` autosave; directory mode keeps explicit Save/Save
    all. Directory handles are stored in IndexedDB for reload reattach;
    if reattachment fails, the text restores as a detached read-only
    copy.
23. **Directory scope**: `structural = false` in Phase 5, so
    add/rename/delete remain virtual-project actions. Browsers without
    `showDirectoryPicker` get a read-only `webkitdirectory` fallback
    with zip export.
24. **Workspace UI**: a compact topbar control shows the active backend
    and name and exposes backend-specific actions.
25. **GitHub (Phase 6a)**: Octokit is lazy-loaded; public repositories are
    readable without a token; private access and commits use a
    fine-grained PAT stored only in `sessionStorage`. Commits are atomic
    through the Git Data API and fast-forward only. Add/rename/delete
    remain disabled for this round. The last repository URL, but never
    the token, is remembered in `localStorage`.

No open product decisions remain. The browser-backend choice is
**wasm_of_ocaml** (§5.8).

## 16. Definition of done

- `make all` and `dune runtest` pass without js_of_ocaml,
  wasm_of_ocaml, Binaryen, or Node installed.
- Phase 0 has recorded measured results for both backends and selected
  **wasm_of_ocaml** with the §5.8 decision rule.
- `make web` produces a self-contained `web/` directory for the selected
  backend (the js_of_ocaml target remains buildable as a documented
  alternative).
- Web CI builds the wasm backend, passes TypeScript and unit tests, and
  enforces the asset-size budgets; lazy chunks are included in the
  published tree.
- Chromium, Firefox, and Safari 18.2+ complete the smoke flow.
- The deployed origin serves `.wasm` as `application/wasm`, resolves
  worker assets under `web/abella_js/`, and permits wasm under CSP.
- `web/index.html`, served statically, can:
  - load each curated multi-file example and compile its imports from
    source on first use, caching the generated `.thc` for the session,
  - show the project's Abella sources and other text files,
  - edit any project file, including imported modules, and recompile
    the affected modules from source,
  - edit non-Abella text files without affecting the prover,
  - download and import the project as a zip with a `project.json`,
  - process the root reasoning file to the cursor and to the end,
  - rewind when an earlier command is edited,
  - show a prominent current Goal plus Abella's proof outcome; other
    messages are in the collapsed Output disclosure; no raw trace is
    shown,
  - reset and start from scratch,
  - restore the project after reload.
- No Angular, jQuery, Bootstrap JS, or Ace in the new page.
- The page is usable in current Chromium and Firefox; if wasm is
  selected, also current Safari 18.2+ (or the chosen backend's documented
  browser floor).
- CLI compatibility tests from §5.1 pass; native Abella behavior is
  unchanged.
- The `Workspace` abstraction is in place even if only the virtual
  backend ships in v1; the local-directory backend is isolated in
  `workspace-directory.ts`, and `abella_doc` “Edit this” plus remote
  backends remain additive.
- If the local-directory backend is unavailable or fails at runtime,
  **Open folder** is absent or reports an error, zip still works, and
  the rest of v1 is unaffected.
- No `abella_doc`-style exporter is present in v1.
